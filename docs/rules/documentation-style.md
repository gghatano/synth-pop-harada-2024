# ドキュメント文体ルール

本リポジトリのドキュメントは、**非技術者にも読める** ことを第一基準にします。
仕様書・Issue・PR・実験レポートのどれであっても、この文体を共通で使います。

---

## 1. 基本原則

1. 1 文を長くしない（目安: 60 字以内、最長でも句読点 2 つまで）
2. 専門用語は初出時に **短い補足** を添える
3. 「何が変わるか / なぜ必要か」を先に書く。実装詳細はその後
4. 箇条書きだけで済ませない。**地の文で背景と意味** を書く
5. 結論から書く。理由は後
6. 読み手を明示して書く（誰に向けた文か自覚する）

---

## 2. 非技術者に配慮する具体策

### 2.1 用語の言い換え・補足

初出時には、短い補足を `（〜のこと）` の形で付けます。

| 専門用語 | 補足の例 |
|---|---|
| SA（Simulated Annealing） | 「焼きなまし法（ランダムに状態を動かしながら徐々に収束させる最適化手法）」 |
| 合成人口 | 「統計的性質が実際の人口と近くなるよう人工的に作った個票集団」 |
| 目的関数 | 「最適化で小さくしたい指標」 |
| 秘匿性 | 「個人が特定されにくいこと」 |
| Gower 距離 | 「数値・カテゴリが混在するデータに使える類似度の測り方」 |

一度補足を付けたあとは、同じドキュメント内では短い形で使ってよい。

### 2.2 禁止表現 / 推奨表現

| 避ける | 使う |
|---|---|
| 「シンプルに実装した」 | 「最小限の機能だけを実装した」 |
| 「ちょっと直した」 | 「〇〇の箇所を 1 行修正した」 |
| 「たぶん動く」 | 「〇〇のケースで動作確認済み」 |
| 「いい感じにした」 | 「〇〇の指標を X から Y に下げた」 |
| 「よしなに」 | 具体の処理内容を書く |

主観的な形容（「よい」「綺麗に」「自然に」）は、できる限り数値か事実で置き換えます。

### 2.3 1 段落 1 論点

- 段落を 1 論点に絞る
- 段落の最初の 1 文に結論を書く（リード文）
- 2 文目以降で根拠や詳細を述べる

### 2.4 箇条書きの使いどころ

- **適切**: 並列な選択肢、ステップ列挙、条件リスト
- **不適切**: 論理の流れを追わせたい説明、因果関係の説明

箇条書きだけの文書は読みやすいように見えて、**論理関係が失われ** ます。箇条書きを使うときも、前後に 1〜2 文の地の文を添えます。

## 3. 文書別の注意

### Issue

- 最初の段落で「誰に・何の価値を」を言い切る
- 背景 → 現状の課題 → 期待する価値 → 成功条件 の順で書く
- 実装手段は書きすぎない（plan で扱う）

詳細: [`issue-driven-development.md`](issue-driven-development.md)

### PR

- 冒頭に「この変更で提供する価値」を 1 文
- 変更内容は **論理単位** で書く（ファイル単位で列挙しない）
- レビュアーに特に見てほしい点を末尾に書く

テンプレ: [`.github/pull_request_template.md`](../../.github/pull_request_template.md)

### 実験レポート

- 最初に「目的・仮説・結果・解釈」の要約を 4 行で書く（非技術者はここだけ読む）
- その後に条件・手順・指標・制約を書く（技術詳細）
- 図には必ずキャプションで「何を主張している図か」を書く

テンプレ: [`docs/templates/experiment_report.md`](../templates/experiment_report.md)

### コード内 docstring / コメント

- **何をするか** はコードで表現し、docstring には **なぜ・どう呼ぶか** を書く
- 引数・戻り値の型はシグネチャに書き、docstring に重複して書かない
- コメントは「WHY が非自明な場合のみ」。「WHAT」を説明するコメントは書かない

## 4. HTML レポート・Issue・PR で文体を揃える

同じ実験・機能について、Issue / PR / HTML レポートの 3 箇所に記述が発生します。それぞれ役割が違うため、コピペせずに役割に応じて書き分けます。

| 文書 | 役割 | 含める内容 |
|---|---|---|
| Issue | なぜやるか | 背景、価値、成功条件、検証方法 |
| PR | 何をしたか / 何を見てほしいか | 変更内容、影響範囲、レビュー観点 |
| HTML レポート | 何が分かったか | 実験結果、解釈、制約、次アクション |

ただし **文体** は揃えます。3 つとも同じ基準（1 文短く、専門用語は補足、結論先出し）で書きます。

---

## 5. 良い文 / 悪い文の比較

### 良い例

> 本変更で、研究者は Gower 距離（数値とカテゴリが混在するデータに使える類似度）の定義を 1 枚のドキュメントで確認できるようになります。これまでは spec.md の §11.4 と §13.3 に分散しており、レビュー時に両方を照合する必要がありました。

- 1 文目: 誰が何を得るか
- 2 文目: なぜこの変更が必要だったか

### 悪い例

> metrics.md を作った。距離の定義を書いた。これで見やすくなったと思う。

- 誰が嬉しいか不明
- 「見やすい」が主観で判断不能
- 何が変わったかが具体でない

## 6. 自己点検チェックリスト

ドキュメントを書き終えたあとに自分に問う:

- [ ] 最初の段落を読んだだけで「誰に何の価値を提供するか」が分かるか
- [ ] 初出の専門用語に短い補足を付けたか
- [ ] 1 文が 60 字を超える箇所がないか
- [ ] 箇条書きだけで説明している論理関係はないか
- [ ] 主観的な形容を数値・事実に置き換えたか
- [ ] 3 日後の自分が読んで意味が取れるか
- [ ] 自分の家族 / 異分野の同僚が読んでも、何のための作業かは分かるか（実装詳細は分からなくてよい）
