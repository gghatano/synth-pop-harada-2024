# Issue 駆動開発ルール

本リポジトリでは、すべての作業を **GitHub Issue** を単位にして進めます。
「Issue を先に立てる」「Issue に記録を残し続ける」を徹底することで、**なぜこの変更が必要だったか** を後から誰でも追えるようにします。

---

## 1. 基本原則

1. コードを変更する前に Issue が存在すること
2. Issue 本文は **価値起点** で書くこと（機能名や実装手段を主語にしない）
3. 各段階の節目で Issue にコメントを残すこと
4. 1 Issue = 1 価値。複数の価値が混ざっているなら分割すること
5. Issue の close は、「実装が終わった」ではなく「**期待した価値が提供され、検証された**」時

---

## 2. Issue のライフサイクル

```
[作成] 0_issue_create
   ↓
[計画] 1_issue_plan         ── Issue に計画コメントを投稿
   ↓
[実装] 2_issue_impl         ── 進捗コメントを随時投稿
   ↓
[自己レビュー] 3_review_and_refactor   ── レビューサマリを投稿
   ↓
[PR] 4_create_pr            ── Issue に PR をリンク
   ↓
[merge & close]
```

各段階の詳細は `.claude/skills/` 配下の skill ファイルを参照。

---

## 3. Issue に必ず含めるもの

段階 0（作成時）に埋めること。テンプレートは [`.github/ISSUE_TEMPLATE/feature_value_driven.md`](../../.github/ISSUE_TEMPLATE/feature_value_driven.md)。

| 欄 | 内容 |
|---|---|
| 背景 | なぜ今この Issue を立てたか。きっかけ・文脈 |
| 現状の課題 | 今何が足りない / 何が困っている |
| 期待する価値 | 利用者視点で 1 文。誰がどう嬉しいか |
| 成功条件 | 測定可能な形で（数値・Yes/No・レポート完成 など） |
| 想定利用者 / 関係者 | 研究者 / 実装者 / 評価者 / 外部関係者 |
| スコープ | 今回やること |
| 非スコープ | 今回やらないこと |
| 想定する検証方法 | どのテスト / どの実験 / どの手順で確認するか |
| 関連ドキュメント | spec / action-plan / 他 Issue / 論文 |

**「実装方針」や「使うライブラリ」は本文に書き過ぎない**。それらは段階 1 で plan に記録します。

---

## 4. Issue コメントの使い方

| 段階 | コメント内容 |
|---|---|
| 計画 | 設計方針・実装方針・テスト観点・実験計画・リスク（テンプレ: [`docs/templates/issue_plan.md`](../templates/issue_plan.md)） |
| 実装開始 | 取り組み始めたこと、最初に触るファイル、作成した worktree 名 |
| 実装中 | 想定と違った観察、方針転換、追加の気付き（3 行程度でよい） |
| 実験 | 実験 ID、条件、速報結果 |
| 自己レビュー | レビューサマリ（テンプレ: [`docs/templates/review_summary.md`](../templates/review_summary.md)） |
| PR 作成 | PR へのリンク |
| merge 後 | 実験結果の最終要約、残課題の新規 Issue 番号 |

コメントは **追記**。過去のコメントを書き換えないこと。方針が変わったら「前のコメントは ~ の理由で修正する」と **新しいコメント** で明示します。

## 5. 良い Issue と悪い Issue の比較

### ✅ 良い例: 価値起点

```
タイトル: [phase-0] 秘匿性評価者が Gower 距離の定義を 1 箇所で参照できるようにする

## 背景
spec §13 と §11.4 に距離の定義と目的関数が分散しており、レビュー時に根拠が追いにくい。

## 現状の課題
- 評価担当が距離の前提を spec 全体から探す必要がある
- レビュー指摘 review-privacy.md §2 でも指摘済み

## 期待する価値
秘匿性評価を担当する研究者が `docs/spec/metrics.md` 1 枚を読むだけで、
使用距離・正規化・重みの根拠を把握できる。

## 成功条件
- Gower / L1 / TV のそれぞれについて、式・正規化・適用先評価指標・根拠論文が 1 テーブル
- 新規メンバーが 10 分以内に距離選択の理由を口頭説明できる

## スコープ
- `docs/spec/metrics.md` 新設
- spec.md §13 から metrics.md への参照差し替え

## 非スコープ
- 距離計算そのものの実装
- 評価器コードの変更

## 想定する検証方法
- 新規メンバー 1 名に読んでもらい、理解度をヒアリング
- spec.md からの参照が壊れていないことを markdown-link-check で確認

## 関連
- review-privacy.md §2
- action-plan.md Phase 0
```

### ❌ 悪い例: 実装主語

```
タイトル: metrics.md を作る

## 本文
Gower 距離とか L1 距離とかの定義を書く。
```

何のためか、誰が嬉しいか、何を持って完了かが無いため、レビュー時に判断基準が無い。

## 6. Issue 命名規則

- 形式: `[phase-<番号>] <価値を示す短い動詞句>`
- 動詞は利用者の視点（「〜できるようにする」「〜を減らす」）
- 実装手段（「〜を実装する」「〜をリファクタする」）は避ける

### 例

- ✅ `[phase-1] 研究者が 100 万人規模の合成人口を 1 時間で生成できるようにする`
- ✅ `[phase-3.5] 評価者が生成結果の類似度を 1 コマンドで確認できるようにする`
- ✅ `[phase-0] 新規メンバーが 30 分でリポジトリ全体像を把握できるようにする`
- ❌ `SA ソルバーを実装`
- ❌ `ドキュメント整備`

---

## 7. Issue を close する条件

以下がすべて満たされた時:

- [ ] 対応 PR が develop に merge されている
- [ ] 成功条件が検証されている（実験 / テスト / レビュー）
- [ ] 実験結果が HTML レポート化され、Issue からリンクされている
- [ ] 残課題が別 Issue として登録されている

`Closes #<番号>` を PR に書いて自動 close させる運用でよいが、**その PR merge 時点で上の条件を満たしていること** を確認してから merge する。

---

## 8. 実装メモだけの Issue にしない

「リファクタリング」「クリーンアップ」「○○ の調査」のような Issue も、必ず価値欄を書きます。
書けない場合は、その Issue は本当に今必要な作業ではない可能性があります。

| 苦しい書き方 | 改善後 |
|---|---|
| 「コードを綺麗にする」 | 「実装者が SA モジュールの変更点を 5 分以内に把握できるようにする」 |
| 「ドキュメントを更新する」 | 「新規メンバーが Gower 距離の定義を即座に参照できるようにする」 |
| 「調査する」 | 「polars 導入の採否を決められる比較データを用意する」 |

---

## 9. チェックリスト

### Issue 作成時
- [ ] 想定読者を 1 人に絞った
- [ ] 価値を 1 文で書いた
- [ ] 成功条件が測定可能
- [ ] スコープ / 非スコープが分かれている
- [ ] 検証方法を先に書いた
- [ ] 関連ドキュメントをリンクした

### Issue クローズ前
- [ ] 成功条件が全て満たされた
- [ ] PR が merge された
- [ ] 実験結果が記録されている
- [ ] 残課題が別 Issue になっている
