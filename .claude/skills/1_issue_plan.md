# SKILL: 1_issue_plan — 実装前の計画を固める

## 目的

段階 0 で「何のためにやるか」が決まった Issue に対し、**どう実現するか** をコードを書く前に確定させる。
ここで設計・テスト・実験計画を合意しておくことで、後戻りと手戻りレビューを減らす。

## 使う場面

- 対象 Issue が段階 0 を満たし、価値・成功条件が明確になった後
- 複数の実現手段が考えられ、選択の根拠を残したいとき
- 実験を伴う作業で、条件・指標を固定してから走らせたいとき

## 入力

- 対象の Issue 番号と本文
- 関連する `docs/spec/spec.md` の該当章、`docs/reviews/action-plan.md` の該当 Phase
- 既存コード（もしあれば）の該当モジュール

## 実施手順

1. **Issue を読み直し、成功条件を再確認する**
   成功条件が曖昧だと plan も曖昧になる。曖昧なら 0_issue_create に戻る。
2. **設計方針を書く**
   - 採用するデータ構造・モジュール境界・依存関係
   - Protocol で切る箇所と、内部で NumPy 並列配列に閉じる箇所の線引き
3. **実装方針を書く**
   - 変更するファイル・追加するファイル
   - 既存コードとの後方互換の扱い
4. **テスト観点を列挙する**
   - 単体テスト（純関数の境界）
   - 結合テスト（複数モジュールを通す）
   - 回帰テスト（過去のバグ再発防止）
   - 性質ベーステスト（入力空間が広い場合）
5. **実験計画を書く**（実験を伴う場合）
   - 仮説（事前登録に近い形で書く）
   - 条件の組み合わせ・繰り返し数・seed
   - 使用データと前処理
   - 評価指標とその出力先
   - 成功 / 失敗の判定基準
6. **リスクと代替案を書く**
   - 想定される失敗モード（実装・計算・解釈）
   - Plan B（途中で切り替える条件）
7. **Issue コメントとして計画を貼る**
   雛形: [`docs/templates/issue_plan.md`](../../docs/templates/issue_plan.md)。
   `gh issue comment <N> --body "$(cat <<'EOF' ... EOF)"` で投稿する。

> **注記**: worktree / branch 作成は本 skill の所掌から外れた。
> [`pm_sop.md`](pm_sop.md) §「親セッションの責務」と [`auto_run_issue.md`](auto_run_issue.md) §1（worktree 作成）が担当する。
> plan を書く時点で worktree は親セッション側で既に用意されている前提で良い。

> **注記**: `docs/plans/issue-<番号>.md` への外出し選択肢は撤廃された（**Issue コメントに統一**）。
> Issue コメントに収まらないほど長大な計画になる場合は、Issue 自体を分割する候補と考える。

## 出力物

- Issue コメントに計画を記録（`gh issue comment <N> --body ...`）

## 完了条件

- [ ] 設計方針・実装方針・テスト観点・実験計画・リスクの 5 項目が揃っている
- [ ] 成功条件が「どのテストが通ればよいか」まで落ちている
- [ ] 計画が Issue コメントとして参照可能

## 注意点

- **「やってみないと分からない」で済ませない**。最低限の仮説でよいので明文化する。探索が必要ならその探索自体を計画に入れる
- 実装方針で迷うなら、**代替案を 2 つ以上書いて採用理由を残す**。後で「なぜこう決めたか」を説明できる
- 実験計画を書くときは、「**この結果なら成功とみなす**」を先に決める。結果を見てから判定基準をずらさない（後付け合理化の防止）
- plan は「変更しない約束」ではない。実装中に前提が崩れたら **Issue コメントで追記** してから方針転換する

## 良い plan の例（ダイジェスト）

> **設計方針**: SA のイテレーションは `domain/protocols.py::Distribution` 経由で差分更新を受け取る。内部表現は NumPy 構造化配列 `Pop` のまま。
>
> **実装方針**: 追加ファイル `optimize/sa.py`、`optimize/delta.py`。既存の `io/*` は触らない。
>
> **テスト観点**:
> - [単体] `delta.apply` が元配列を破壊しない
> - [単体] 目的関数の差分計算と全計算の結果が 1e-9 以内で一致
> - [結合] 小規模データで 1000 iter 回し、収束傾向を確認
> - [回帰] 過去に報告された NaN 発生ケース（Issue #17）を再現しないこと
>
> **実験計画**: 小規模（N=10k）で seed×5 ×温度スケジュール×3 = 15 run。目的関数の減衰曲線が単調減少であれば成功。
>
> **リスク**: 差分更新の数値誤差が蓄積すると長時間 run で本計算と乖離する。Plan B: 100 iter ごとに本計算で検算。

## GitHub Issue に書くべきこと（段階 1 終了時点）

- [ ] 設計方針（何を変え、何を変えないか）
- [ ] 実装方針（ファイル単位で）
- [ ] テスト観点（レイヤ別に）
- [ ] 実験計画（仮説・条件・指標・判定）
- [ ] リスクと代替案
- [ ] 親セッションが用意した worktree / branch 名（参考情報として）
