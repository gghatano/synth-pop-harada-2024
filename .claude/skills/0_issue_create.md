# SKILL: 0_issue_create — 価値起点で Issue を作る

## 重要な制約

- ファイルの作成・編集は一切行わない
- コードの実装は一切行わない
- Issue を作成したら即座に終了する（worktree 作成・plan 作成は段階 1 以降の所掌）

## 目的

次に取り組む作業を、**実装タスク** ではなく **「誰にどんな価値を提供するか」** を起点とした GitHub Issue に落とす。
ここで価値が曖昧な Issue は、後の plan / impl / review すべてで迷走するので、ここを雑にしない。

## 使う場面

- 新しい機能・実験・改善を始めたいとき
- 議論や会話の中で「これやった方がいいよね」と出た事柄を、作業可能な単位に変換したいとき
- バグ報告や既存 Issue のリスプリットを行うとき

## 入力

以下のうち、手元にあるものを集める（足りなければ質問で引き出す）:

- 話題のきっかけ（会話ログ・レビュー指摘・仕様書の章番号 など）
- 誰のための作業か（研究者 / 実装者 / ステークホルダー / 将来の自分）
- 現状の痛みや不足
- 関連する既存ドキュメント（`docs/spec/spec.md`、`docs/reviews/action-plan.md` の章番号 など）

## 実施手順

1. **想定読者を 1 人に絞る**
   「この Issue を最初に読むのは誰か？」を 1 人だけ決める。全員向けに書かない。
2. **価値を 1 文で言い切る**
   「〜ができるようになる」「〜の判断材料が得られる」など、利用者の視点で書く。
   機能名（"SA を実装する"）ではなく、もたらされる変化（"100 万人規模の合成人口を 1 時間以内に生成できるようになる"）を主語にする。
3. **背景・課題 → 価値 → 成功条件 の順に本文を組み立てる**
   テンプレート: [`.github/ISSUE_TEMPLATE/feature_value_driven.md`](../../.github/ISSUE_TEMPLATE/feature_value_driven.md)
4. **スコープと非スコープを分ける**
   「今回やらないこと」を 2〜3 個書いて境界を明示する。書かないと後で膨らむ。
5. **検証方法を先に書く**
   「何を測れば成功と言えるか」を、実装方法より先に確定する。
6. **関連 Issue / ドキュメントをリンク**
   `docs/spec/spec.md` の章、`docs/reviews/action-plan.md` のフェーズ番号、前後関係のある Issue 番号を列挙する。
7. **タイトルを整える**
   形式: `<価値を示す短い動詞句>`
   例: `研究者が Gower 距離の定義を 1 箇所で参照できるようにする`
   過去のフェーズ番号接頭辞 `[phase-N]` は撤廃済（フェーズ列挙の保守コストが利益を上回ったため）。
   利用者視点の動詞句のみで構成する。

## 出力物

- GitHub Issue 1 枚（`.github/ISSUE_TEMPLATE/feature_value_driven.md` の形式を満たす）
- 関連があれば `docs/tasks/phase-NN/task-MMM.md` を追加（グローバル規約に従う）

## 完了条件

- [ ] 価値が 1 文で書かれている
- [ ] 成功条件が測定可能な形で書かれている
- [ ] スコープ / 非スコープが分かれている
- [ ] 検証方法が書かれている
- [ ] 非技術者が読んで「何のためにやるか」が分かる

## 注意点

- **実装手段を Issue 本文に書き過ぎない**。実装方針は段階 1 (`1_issue_plan`) で扱う
- 「リファクタリング」「クリーンアップ」のような Issue も、**なぜ今それが必要か**（誰にどう効くか）を必ず書く
- 1 Issue = 1 価値。複数の価値が混ざっていたら Issue を分ける
- PR は後から別途作る。Issue 作成時点ではブランチや worktree はまだ作らない

## 良い Issue と悪い Issue

### 良い例

> **タイトル**: `秘匿性評価の距離定義を 1 箇所に集約し、評価者が根拠を即座に辿れるようにする`
>
> **背景**: 現状 spec §13 の距離定義と §11.4 の目的関数が別箇所に散っており、レビュー時に「この Gower 距離は何を前提にしているのか」が追いにくい。
>
> **価値**: 秘匿性評価を担当する研究者が `docs/spec/metrics.md` 1 枚を読むだけで、使用距離・正規化・重みの根拠を把握できる。
>
> **成功条件**: Gower / L1 / TV のそれぞれについて、式・正規化・適用先評価指標・根拠論文が 1 テーブルに揃う。新規メンバーが 10 分以内に距離選択の理由を説明できる。

### 悪い例

> **タイトル**: `Gower 距離を実装する`
>
> **本文**: `numpy で Gower 距離の関数を作る。`

理由: 誰のためか、今なぜ必要か、何をもって完了かが無い。

- [ ] スコープ / 非スコープ
- [ ] 想定する検証方法
- [ ] 関連ドキュメント・Issue
