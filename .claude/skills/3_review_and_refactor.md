# SKILL: 3_review_and_refactor — 自己レビューと整理

## 目的

PR を出す前に、**自分で自分の変更を厳しく読む** ことで、レビュアーの負荷を減らし、実験結果の妥当性を確認する。
「動くようになった」を超えて、「他人が読んで意図を追えるか」「結果を第三者が再現できるか」まで引き上げる。

## 使う場面

- `2_issue_impl` で計画上のテスト観点をすべて満たした後
- 実装が一段落し、PR 作成の前に自己チェックしたいとき
- レビューコメントを受けて再整理するとき

## 入力

- 対象 Issue と実装済みの branch（worktree 上）
- 段階 1 の計画（plan）と段階 2 の実装メモ

## 実施手順

1. **テスト結果を最終確認する**
   ```bash
   uv run pytest -x --cov=src --cov-report=term-missing
   ```
   - 全テストが green であることを確認
   - カバレッジの抜けが計画の想定と合致するか確認（計画で挙げたテスト観点が本当に実装されているか）
2. **`git diff develop..HEAD` を読み直す**
   - 他人の目で差分を読む。5 分休憩してから読むと発見が増える
   - 自分のコミットメッセージで、変更の意図が追えるか確認
3. **設計負債を棚卸しする**
   以下の観点でコードを点検:
   - 重複コード（DRY）
   - 責務の混在（1 関数に読み込み・変換・書き出しが混ざっていないか）
   - 早すぎる抽象化（使われていない Protocol / 汎用クラス）
   - マジックナンバー・ハードコード
   - Protocol と実装の境界が壊れていないか
4. **可読性を点検する**
   - 命名は意味を表しているか（`x`, `tmp`, `do_it` は禁止）
   - 1 関数が長すぎないか（目安 50 行以内）
   - docstring が「何のために呼ぶか」を書いているか
5. **非技術者向け説明可能性を点検する**
   - Issue の「背景」「価値」「成功条件」を読み返し、今の実装がそれを満たすと自信を持って言えるか
   - 実験結果を、指標名だけでなく **含意（何が分かったか）** として書けるか
   - 1 段落の要約を試し書きしてみる（後で PR 本文に使える）
6. **再現性を点検する**
   - seed が config に固定されているか
   - 入力データのバージョン・パスが明記されているか
   - 実行コマンドが `experiments/<...>/report.md` の「再現手順」欄に書かれているか
   - 同じ条件で 2 回走らせて、結果が一致するかスポットチェック
7. **実験結果の妥当性を点検する**
   - 想定した方向の変化か（増えるはずが減っていないか）
   - 極端値・NaN・Inf が混入していないか
   - ベースラインとの比較が妥当か（サンプルサイズ・繰り返し数が十分か）
   - 結果が仮説を支持しない場合、どこまで追加実験が必要かを判断
8. **リファクタリングを行う**
   - 4 / 5 で見つけた負債のうち、**本 Issue の範囲内** で直せるものを直す
   - 範囲外のものは新規 Issue として切り出し、本 PR には含めない
   - リファクタ後に全テストが green のまま維持されていることを確認
9. **追加実験の必要性を判断する**
   - 結果が仮説を支持するなら追加実験は不要
   - 結果が曖昧なら、条件・繰り返し数を絞った追試を 1 回だけ走らせる
   - 結果が仮説を覆すなら、原因を最低 1 つ立てて追加実験で確認する
10. **レビューサマリを書いて Issue に貼る**
    雛形: [`docs/templates/review_summary.md`](../../docs/templates/review_summary.md)

## 出力物

- Issue コメントに「レビューサマリ」
- 必要に応じてリファクタの追加コミット
- 追加実験を行った場合はその実験ディレクトリ

## 完了条件

- [ ] 全テストが green
- [ ] 設計負債の棚卸し結果が記録されている（見つかった / 見つからなかった を含む）
- [ ] 非技術者向け 1 段落要約が書ける
- [ ] 再現手順が実際に通ることを確認済み
- [ ] 実験結果の解釈が記録されている
- [ ] レビューサマリが Issue に貼られている

## 注意点

- **「自分で書いたから分かる」は禁句**。3 日後の自分が読めるか、を基準にする
- **範囲を広げない**。無関係なリファクタは別 Issue に分ける。この段階で PR が肥大化すると、誰もレビューできなくなる
- 実験結果が想定と違うときほど、**結果を書き換えずに解釈を書く**。失敗も記録対象
- 可読性の修正は、テストのない箇所で暴れない。テストがないなら先にテストを足してから直す

## リファクタリング方針の判断基準

| 状況 | 方針 |
|---|---|
| テストで守られており、本 Issue の文脈内の負債 | 本 PR で直す |
| テストで守られているが、本 Issue の範囲外 | 新規 Issue に分離。本 PR ではコメントだけ追加 |
| テストで守られていない | 先にテストを追加してから判断 |
| Protocol / 公開 API に関わる | 単独 Issue で扱う（影響範囲が広いため） |

## GitHub Issue に残すべきレビューサマリ

以下の構成で Issue コメントとして投稿する:

1. **テスト結果**: 件数、カバレッジ、落ちた履歴
2. **実装で分かったこと**: 計画との差分、仕様メモ
3. **実験結果の解釈**: 非技術者にも通じる 1 段落
4. **見つかった負債と対応**: 直したもの / 別 Issue 化したもの
5. **残課題**: 次の Issue で扱うべき内容
6. **レビュアーに見てほしい点**: 設計判断 / 実験結果の妥当性 など
